# script-builder draft-script schema

The contract for one draft bash script under `.claude/scripts/drafts/<source_pattern_id>.sh.draft`. Each draft is a starting point the user reviews, optionally edits, then promotes into `.claude/scripts/` with a descriptive name.

This schema is what:
- **`script-builder`** (v1.1+ Phase 3) writes — one draft per approved-script capture.
- **The user** reads, optionally edits, and promotes — the contract describes what to expect.
- **The wider skeleton convention** — promoted scripts under `.claude/scripts/*.sh` follow the same 5-section discipline. Drafts ship the convention pre-applied so promoted scripts are coherent with `commit.sh`, `deploy.sh`, `install.sh`.

## File format

UTF-8 bash with `.sh.draft` filename suffix. The `.draft` makes the file not pick up as a normal `.sh` script in tools that filter by extension — drafts cannot be accidentally executed even if they have a shebang. The user explicitly renames to `.sh` and `chmod +x` on promote.

Filename: `<source_pattern_id>.sh.draft` where `<source_pattern_id>` is the capture's pattern_id (which is also the observation's `pattern_id`). The id-as-filename is what makes idempotency direct — `script-builder` checks for an existing file by name before drafting.

## Five-section discipline

Every draft script has five sections in order. Sections may be empty (a one-shot script may have no helpers); the order is what matters.

### 1. Shebang + strict mode

```bash
#!/usr/bin/env bash
# DRAFT — generated by script-builder from approved capture.
# Source capture:    .claude/captures/<source_pattern_id>.md
# Source pattern_id: <source_pattern_id>
# To promote:
#   1. Review / edit this draft.
#   2. mv .claude/scripts/drafts/<id>.sh.draft .claude/scripts/<descriptive-name>.sh
#      chmod +x .claude/scripts/<descriptive-name>.sh
#   3. Edit capture frontmatter:
#      status: approved → shipped
#      add: shipped_to: .claude/scripts/<descriptive-name>.sh
set -uo pipefail
```

The `set -uo pipefail` floor is non-negotiable per plugin discipline rule 6. Many scripts also want `set -e` — include it when the script does multi-step work that should halt on the first error. The header comment block is what makes the draft traceable to the capture (and transitively to the observation). The user may keep or remove the comment block on promote.

### 2. Constants / config

```bash
readonly PROJECT_DIR="${CLAUDE_PROJECT_DIR:?CLAUDE_PROJECT_DIR not set}"
readonly DEFAULT_EXT="gd"
readonly EXCLUDES=( .git .godot .import node_modules build dist )
```

`readonly` for anything that shouldn't be mutated. Validate `$CLAUDE_PROJECT_DIR` with the `${VAR:?msg}` pattern (cite source: `template/.claude/hooks/sessionend-observe.sh:13`). Group defaults near the top so a tuning user finds them fast.

### 3. Helpers

```bash
usage() {
  echo "Usage: $0 [ext]" >&2
  echo "  ext defaults to 'gd'" >&2
  exit 1
}

err() {
  echo "ERROR: $*" >&2
  exit 2
}
```

Small functions for repeated logic. Optional for one-shot scripts; required when the main logic would duplicate the same five-line block more than twice. `>&2` redirection for error output so callers can pipe stdout cleanly.

### 4. Main logic

```bash
EXT="${1:-$DEFAULT_EXT}"

# Path-shape guard: reject obvious file-path shapes for the ext arg.
case "$EXT" in
  */*) err "ext should be a bare extension (e.g. 'gd'), not a path" ;;
esac

# Validate prereq.
command -v find >/dev/null 2>&1 || err "find not on PATH"

# bash-safety excludes baked in.
EXCLUDE_ARGS=()
for d in "${EXCLUDES[@]}"; do
  EXCLUDE_ARGS+=( -path "./$d" -prune -o )
done

find "$PROJECT_DIR" "${EXCLUDE_ARGS[@]}" -name "*.${EXT}" -print | wc -l
```

The actual work. Inputs validated at the boundary (path-shape guards reject obvious mistakes — cite `template/.claude/scripts/commit.sh:23-31` for the pattern). Fail-fast on missing prerequisites via `command -v` / `[ -f ... ]` / `[ -d ... ]` checks. If the script does recursive scans, **`bash-safety` conventions apply**: noise-path excludes baked into the command shape, `timeout` wrap if runtime is unbounded, `-maxdepth` where the recursion bound is known.

### 5. Cleanup / error handling / exit

```bash
# Explicit exit codes:
#   0 = success
#   1 = usage error (handled in usage())
#   2 = validation failure (handled in err())
exit 0
```

Explicit `exit <code>` with codes documented in the script header or here. `0` is success; `1` is conventional for usage / arg errors; `2` for validation failures; project-specific codes for project-specific failures. `trap '...' ERR` is required when the script mutates state and needs to roll back; optional otherwise.

## Path-shape guards (load-bearing patterns)

Generated scripts include these guards as appropriate to their function:

- **`$CLAUDE_PROJECT_DIR` validation**: `${CLAUDE_PROJECT_DIR:?CLAUDE_PROJECT_DIR not set}`. Source: [`template/.claude/hooks/sessionend-observe.sh`](../../hooks/sessionend-observe.sh) line 13.
- **First-arg path-shape rejection**: when the first arg should be a string (commit message, label, identifier), reject inputs that look like file paths or have code-file extensions. Source: [`template/.claude/scripts/commit.sh`](../../scripts/commit.sh) lines 23–31.
- **Prerequisite-file existence**: `[ -f "$path" ] || err "missing: $path"` for any file the script reads.
- **Prerequisite-directory existence**: `[ -d "$dir" ] || err "missing dir: $dir"` for any directory the script walks.
- **Dependency on PATH**: `command -v <bin> >/dev/null 2>&1 || err "<bin> not on PATH"` for any binary the script invokes that isn't in POSIX baseline.

## Error handling conventions

- **`set -uo pipefail`** is the floor. `-u` catches unset variables; `-o pipefail` propagates failures through pipes.
- **`set -e`** when the script halts on the first error (most scripts). Skip when the script handles errors explicitly.
- **`trap '...' ERR`** for scripts that mutate state (write files, modify config). Cleanup on error path.
- **Exit codes are documented** in the script header or near the `exit` calls. Don't use bare `exit` or arbitrary numbers without explanation.
- **`>&2` redirection** for error messages. Stdout is for the script's primary output; stderr is for diagnostics.

## bash-safety integration

Generated scripts that do **any recursive scan** MUST follow the conventions in [`template/.claude/skills/bash-safety/SKILL.md`](../../skills/bash-safety/SKILL.md):

- **Noise-path excludes**: `.git`, `.godot`, `.import`, `node_modules`, `build`, `dist`, `out`, `target`, `.next`, `.nuxt`, `__pycache__`, `.pytest_cache`, `.venv`, `venv`, `.idea`, `.vscode`, `coverage`, `vendor`. Bake into the `find` / `grep -r` / `rg` invocation as appropriate.
- **`timeout`** wrap on operations whose runtime is unbounded by `-maxdepth` or a known small input set.
- **`-maxdepth N`** when the recursion shouldn't go past `N` levels — cheaper than excludes and faster.
- **`&` paired with `wait` / `kill` / `disown`** — never naked. Zombies are silent and accumulate.

If the capture's pattern is itself a recurring bash command — which is common for `pattern_type: repeated_command` captures — the draft script's job is to **bake the bash-safety conventions into the canonical shape**. That's the actual value proposition of capturing the command as a script: it stops being re-derived from scratch with a different mistake each time.

## Naming convention

- **Draft filename**: `<source_pattern_id>.sh.draft`. The `.sh.draft` suffix is the "don't run me yet" marker. The id-as-filename gives direct idempotency.
- **Promoted filename**: `<descriptive-name>.sh`, chosen by the user. Kebab-case lowercase. Examples: `count-files-by-ext.sh`, `validate-routing.sh`, `backup-claude-state.sh`. The promoted name should describe what the script does in 2–4 hyphenated words.

The promoted filename is NOT tracked by `script-builder` (the agent never reads `.claude/scripts/`). The traceability link is in the capture frontmatter — the user records `shipped_to: .claude/scripts/<descriptive-name>.sh` on promote.

## Complete realistic example

A representative draft script — ~45 lines, all 5 sections populated, demonstrates path-shape guards, bash-safety integration, error handling. Generated from the canonical `count-godot-files` example in the workflow-suggester schema.

```bash
#!/usr/bin/env bash
# DRAFT — generated by script-builder from approved capture.
# Source capture:    .claude/captures/a3f5b2e1c4d8...md
# Source pattern_id: a3f5b2e1c4d8...
# To promote:
#   1. Review / edit this draft.
#   2. mv .claude/scripts/drafts/<id>.sh.draft .claude/scripts/count-files-by-ext.sh
#      chmod +x .claude/scripts/count-files-by-ext.sh
#   3. Edit capture frontmatter:
#      status: approved → shipped
#      add: shipped_to: .claude/scripts/count-files-by-ext.sh
set -uo pipefail

# --- 1. Shebang + strict mode (above) ---

# --- 2. Constants / config ---
readonly PROJECT_DIR="${CLAUDE_PROJECT_DIR:?CLAUDE_PROJECT_DIR not set}"
readonly DEFAULT_EXT="gd"
readonly EXCLUDES=( .git .godot .import node_modules build dist out target
                    .next .nuxt __pycache__ .pytest_cache .venv venv
                    .idea .vscode coverage vendor )

# --- 3. Helpers ---
usage() {
  echo "Usage: $0 [extension]" >&2
  echo "  extension: bare extension without dot, defaults to '$DEFAULT_EXT'" >&2
  exit 1
}

err() {
  echo "ERROR: $*" >&2
  exit 2
}

# --- 4. Main logic ---
EXT="${1:-$DEFAULT_EXT}"

# Path-shape guard: reject path-shaped or dotted args.
case "$EXT" in
  */*|.*) err "extension should be bare (e.g. 'gd'), got '$EXT'" ;;
esac

command -v find >/dev/null 2>&1 || err "find not on PATH"

EXCLUDE_ARGS=()
for d in "${EXCLUDES[@]}"; do
  EXCLUDE_ARGS+=( -path "./$d" -prune -o )
done

cd "$PROJECT_DIR" || err "cannot cd to PROJECT_DIR: $PROJECT_DIR"
find . "${EXCLUDE_ARGS[@]}" -name "*.${EXT}" -print | wc -l

# --- 5. Cleanup / exit ---
# Exit codes:
#   0 = success (count printed)
#   1 = usage error
#   2 = validation / prereq failure
exit 0
```

That file is 45 lines including the header comment block — comfortably in the 30–80 line target. All five sections present. `bash-safety` excludes baked in. Path-shape guard on the `EXT` arg matches the pattern from `commit.sh`. Exit codes documented.

## What NOT to put in drafts

- **Hardcoded secrets**: never. The capture schema's redaction rules ensure evidence is clean; the draft must not re-introduce secrets in defaults or comments.
- **Long inline documentation**: brief comments explaining non-obvious choices are fine; multi-paragraph essays belong in the capture, not the script. If the script needs more explanation, it's probably under-baked.
- **Calls out to the network** for anything not load-bearing to the script's purpose. Hook scripts in particular must not call out to the network (plugin discipline rule 2 — relevant for the hooks pattern, conceptually adjacent here).
- **`sudo` / privileged operations** without explicit user warning in the usage block.
- **Side effects on directories outside `$CLAUDE_PROJECT_DIR`** without clear justification. Stay in the project tree.

If the captured pattern can't fit the 5-section discipline within ~80 lines, the pattern is probably under-normalized or the artifact type was wrong (it should have been an `agent`, not a `script`). Flag back to the user via the agent's status report — don't pad.
